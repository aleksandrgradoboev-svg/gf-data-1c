# gt-data-1c

MCP-сервер доступа к данным информационных баз 1С:Предприятие. Только чтение.

Отвечает агенту на вопросы «сколько продали», «что на складе», «какие поля у документа»,
обращаясь к расширению, установленному в самой базе. Метаданные конфигурации и код —
не его дело: он про **данные**.

## Из чего состоит

| Часть | Где | Что делает |
|---|---|---|
| Сервер | `cmd/gtdata`, `internal/` | говорит с агентом по MCP (stdio), держит реестр баз, ходит в базы по HTTP |
| Расширение 1С | `extension/module`, `build/*.json` | HTTP-сервис внутри базы: метаданные, запросы, итоги регистров, журнал |
| Сборка расширения | `build/build-extension.ps1` | собирает исходники расширения под конкретную конфигурацию |

## Инструменты

| Инструмент | Назначение |
|---|---|
| `bases` | реестр баз: список, добавить, убрать, назначить базу по умолчанию |
| `probe` | жив ли канал; различает погашенный веб-сервер, отсутствие расширения и отказ прав |
| `base_info` | конфигурация, версия, платформа, режим совместимости |
| `metadata` | состав конфигурации: сводка по категориям или перечень объектов категории |
| `object` | реквизиты, табличные части, измерения, ресурсы, значения перечисления |
| `query_check` | разбор текста запроса без обращения к данным |
| `query` | запрос на языке 1С (только ВЫБРАТЬ) |
| `count` | число записей таблицы с отбором |
| `register` | остатки и обороты регистра накопления |
| `slice` | срез регистра сведений — цены, курсы, ставки, действующие на дату |
| `accounts` | бухгалтерские итоги по счёту: остатки, обороты, полная картина |
| `eventlog` | журнал регистрации |

Два правила, которые продукт держит жёстко:

1. **Отказ никогда не выглядит как пустой результат.** Ответ, начинающийся словом `ОТКАЗ`,
   говорит о вызове, а не о содержимом базы. Пустая выборка, наоборот, прямо сообщает,
   что запрос выполнен и вернул ноль строк.
2. **Базу называют явно.** Незнакомое имя даёт отказ с перечнем известных, а не молчаливый
   уход в базу по умолчанию.

## Сборка

```powershell
# расширение (одна сборка на любую базу) — кладётся внутрь пакета установщика
powershell -File build/build-extension.ps1 -OutputDir internal/installer/extension

go build -o bin/gtdata.exe ./cmd/gtdata          # сервер вместе с расширением внутри
go test ./internal/...                            # тесты (живые пропускаются без стенда)
```

Расширение намеренно **не заимствует язык** расширяемой конфигурации и собрано с низким
режимом совместимости. Это и делает одну сборку пригодной для любой базы: расширение с
собственным языком привязывается к UUID языка конкретной конфигурации и в другую не встаёт,
а режим совместимости выше базы платформа отвергает. Проверено на УТ 11.5 и БП 3.0.

Исходник расширения — описание (`build/httpservice.json`, `build/role.json`,
`extension/module/GT_Data.bsl`), а не готовая выгрузка.

## Установка в базу

```powershell
# файловую базу веб-сервер держит занятой — на время установки его гасят
Stop-Process -Name httpd -Force
gtdata.exe -install "C:\путь\к\базе" -db-user <пользователь> -db-password <пароль>
Start-Process C:\Users\User\tools\apache24\bin\httpd.exe

# серверная база
gtdata.exe -install "сервер\база" -server -db-user <пользователь> -db-password <пароль>
```

Установщик несёт расширение внутри бинаря, сам находит конфигуратор (старшую версию
платформы; иное — флагом `-platform`) и проверяет результат **по журналу конфигуратора**,
а не по коду возврата: `1cv8.exe` — оконное приложение и умеет отрапортовать успехом,
застряв на диалоге.

Роль `GT_ОсновнаяРоль` объявляется основной ролью конфигурации, поэтому доступ к сервису
получает любой пользователь базы. Если библиотека стандартных подсистем в конкретной базе
считает основные роли и лишняя запись роняет сеанс — соберите расширение с
`-StripDefaultRole` и выдайте роль вручную. Права на **данные** расширение не выдаёт и не
подменяет: их даёт роль пользователя в самой конфигурации.

## Регистрация базы у сервера

```
bases action=add name=<ключ> url=http://<хост>/<база>/hs/gt-data user=… password=…
```

Реестр лежит в профиле пользователя (`%AppData%/gt-data-1c/bases.json`, права 0600 —
там пароли). Регистрация самого сервера у агента сводится к пути бинарника.

## Диагностика

| Флаг | Что делает |
|---|---|
| `-log auto` | вести журнал обращений к базам (`%LocalAppData%/gt-data-1c/server.log`) |
| `-timeout` | сколько ждать базу; по умолчанию 300 с — выгрузка метаданных крупной конфигурации идёт минутами |
| `-registry` | другой файл реестра баз |
| `-version` | версия, путь реестра и путь журнала |

Инструмент `probe` сверяет версию расширения с версией сервера и предупреждает при
расхождении. Это не формальность: старое расширение отвечает на новые методы **пустотой,
а не ошибкой**, и рассинхрон читается как «в базе нет данных».

Ответ базы крупнее 128 МиБ отклоняется с внятным отказом — такой размер почти всегда
означает ошибку запроса, а не большие данные.

## Проверки

```
go test ./internal/...                      # всё: каркас, живые прогоны, приёмка
go test ./internal/server/ -run Приёмка     # только приёмка
GT_SKIP_LIVE=1 go test ./internal/...       # без обращения к стендам
```

Живые тесты сами пропускаются, если стенд не отвечает: на машине без базы прогон обязан
молчать, а на машине с базой — падать, если база ответила не то. Приёмка сверяет числа
с эталоном, снятым прежним каналом, и проверяет, что все типы объектов, которые он понимал,
понимает и этот.
