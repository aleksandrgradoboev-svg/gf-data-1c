# gf-data-1c

MCP-сервер доступа к данным информационных баз 1С:Предприятие. Только чтение.

Отвечает агенту на вопросы «сколько продали», «что на складе», «какие поля у документа»,
обращаясь к расширению, установленному в самой базе. Метаданные конфигурации и код —
не его дело: он про **данные**.

## Чем отличается

Продукт написан против одного класса бед: **агент получает от базы правдоподобное
враньё и строит на нём отчёт.** Отсюда четыре механизма — каждый вырос из конкретного
случая, когда ответ выглядел разумным и был неверным.

**Предупреждения о тихих ловушках.** Опасен не запрос с ошибкой — такой платформа
отвергнет сама. Опасен запрос, который **разбирается, выполняется и отдаёт неверный
результат**. Ссылка, сравненная со строковым литералом, — ноль строк, ошибки нет, и
пустая выборка неотличима от честного «данных нет». Остаток на дату без времени —
берётся на **начало** дня, и отчёт разойдётся с оборотами ровно на движения этого дня.
Такие места разбираются по тексту запроса и приходят предупреждением вместе с успешным
ответом: запрос может быть и намеренным, поэтому предупреждение, а не отказ.

**Текст запроса пишет платформа, а не модель.** `query` выполняет только тот текст,
который в этой же сессии собрал `query_build`. Это механизм, а не строка в промпте:
правило «не сочиняй текст запроса» стояло в инструкции агента и дало 21 отказ подряд
при одном обращении к построителю. Промпт читают, сервер исполняет.

**Отказ обогащается подсказкой.** Платформа отвечает точно, но односложно: «Поле не
найдено "Регистратор"». Человеку этого хватает — он знает, где смотреть; вызывающему
инструмент приходится угадывать, и угадывает он плохо. Замер 25.08.2026: после трёх
таких отказов агент бросает запросы и начинает считать числа вручную по общей выборке —
числа выходят красивые и неверные. Поэтому к отказу дописывается то, что известно и без
обращения к базе: состав полей виртуальных таблиц, сигнатуры их параметров, замены для
конструкций, которых в языке запросов нет.

**Справка вендора, а не память модели.** `syntax` отвечает страницами справки
установленного релиза — 132 страницы языка запросов (`shquery`) и 52 158 страниц по
объектам и таблицам платформы (`shcntx`). Не пересказ и не «как обычно бывает»: язык
дополняется между релизами, и общее знание о 1С стоит здесь ровно столько же, сколько
припомненное имя объекта. Он же с `members=true` отдаёт срез членов типа целиком —
963 типа, 7199 методов, 13 662 свойства, 693 события, 444 конструктора — потому что
справка нарезана по странице на каждый метод, и вопрос «что умеет этот тип» иначе
решается только перебором.

И два свойства, которые держатся жёстко: **отказ никогда не выглядит пустым
результатом** (ответ с `ОТКАЗ` говорит о вызове, а не о содержимом базы), и **базу
называют явно** — базы по умолчанию нет вовсе, потому что «в этой конфигурации такого
нет» без имени базы читается как факт о 1С вообще.

## С чего начать

Чтобы канал заработал, нужны три вещи: бинарь у агента, расширение в базе и запись о базе
в реестре сервера.

```powershell
# 1. Взять сервер — бинарь со страницы релизов: он уже несёт расширение внутри.

# 2. Поставить расширение в базу — установщиком (нужны права администратора базы):
gfdata.exe -install "C:\путь\к\базе" -db-user <пользователь> -db-password <пароль>

#    ...либо руками, готовым файлом dist/GTData.cfe из этого репозитория:
#    Конфигуратор → Конфигурация → Расширения конфигурации → Добавить из файла.
#    Собирать ничего не нужно, файл готовый.

# 3. Рассказать серверу о базе
#    (вызовом инструмента bases у агента, либо правкой файла реестра)
bases action=add name=<ключ> url=http://<хост>/<база>/hs/gt-data user=… password=…
```

Проверка, что всё сошлось, — инструмент `probe`: он различает погашенный веб-сервер,
базу без расширения и отказ прав, а не сводит их к «недоступно».

Регистрация сервера у агента — это путь к бинарнику, без флагов. Для клиента, который не
умеет запускать процессы сам (контейнер, веб), есть сетевой режим: `gfdata.exe -http` —
см. «Диагностика».

## Из чего состоит

| Часть | Где | Что делает |
|---|---|---|
| Сервер | `crates/gf-data-1c` | говорит с агентом по MCP (stdio или HTTP), держит реестр баз, ходит в базы по HTTP |
| Расширение 1С | `extension/module`, `build/*.json` | HTTP-сервис внутри базы: метаданные, запросы, итоги регистров, журнал |
| Сборка расширения | `build/build-extension.ps1` | собирает исходники расширения под конкретную конфигурацию |

## Инструменты

| Инструмент | Назначение |
|---|---|
| `bases` | реестр баз: список, добавить, убрать |
| `probe` | жив ли канал; различает погашенный веб-сервер, отсутствие расширения и отказ прав |
| `base_info` | конфигурация, версия, платформа, режим совместимости |
| `metadata` | состав конфигурации: сводка по категориям или перечень объектов категории |
| `object` | реквизиты, табличные части, измерения, ресурсы, значения перечисления |
| `query_check` | разбор текста запроса без обращения к данным |
| `query` | запрос на языке 1С (только ВЫБРАТЬ) |
| `count` | число записей таблицы с отбором |
| `register` | остатки и обороты регистра накопления |
| `slice` | срез регистра сведений — цены, курсы, ставки, действующие на дату |
| `accounts` | бухгалтерские итоги по счёту: остатки, обороты, полная картина |
| `export` | выгрузка результата запроса в файл (csv/jsonl), когда строк больше тысячи |
| `eventlog` | журнал регистрации |

Два правила, которые продукт держит жёстко:

1. **Отказ никогда не выглядит как пустой результат.** Ответ, начинающийся словом `ОТКАЗ`,
   говорит о вызове, а не о содержимом базы. Пустая выборка, наоборот, прямо сообщает,
   что запрос выполнен и вернул ноль строк.
2. **Базу называют явно, и это обеспечено механизмом.** `base` обязателен у всех инструментов
   данных, базы по умолчанию нет вовсе: вызов без неё отклоняется схемой. Незнакомое имя даёт
   отказ с перечнем известных, а не пустой результат. Отказ называет базу в первой же строке —
   «в этой конфигурации такого нет» без имени базы читается как факт о 1С вообще, и вызывающий
   начинает перебирать имена объекта вместо того, чтобы усомниться в базе.

## Чего продукт не делает — сознательно

Это не список долгов, а границы. Здесь они названы затем, чтобы не выглядеть пробелами.

- **Только чтение.** Запрос на изменение отклоняется до обращения к базе. Это свойство
  продукта, а не ограничение прав пользователя.
- **Только русскоязычные конфигурации.** Имена метаданных и перевод в запросную нотацию
  написаны под русские префиксы.
- **Код и метаданные конфигурации — не сюда.** Поиск по модулям, формы и подсистемы как
  предмет разработки — задача навигационных инструментов по исходникам; здесь речь о данных.
- **Соединения и пакеты не собираются построителем.** Такой вопрос честно возвращается
  как «не собирается», без обходного текста — см. `query_build` ниже.

## Сборка

```powershell
cargo build --release                             # сервер БЕЗ встроенного расширения
cargo test --workspace                            # тесты (живые пропускаются без стенда)
```

Так собранный сервер работает как MCP-сервер полностью, но установить расширение в базу
не может и говорит об этом прямо. Ставить расширение в этом случае нужно готовым файлом
`dist/GTData.cfe` — он лежит в репозитории и собирать его не требуется.

Чтобы собрать сервер **со встроенным расширением** (как в релизах), нужны XML-исходники
расширения. Их раскладывает из описания скрипт `build/build-extension.ps1`, и ему нужен
наш инструментарий сборки объектов 1С — у стороннего разработчика его нет:

```powershell
powershell -File build/build-extension.ps1 -OutputDir crates/gf-data-1c/extension
cargo build --release
```

Правка самого расширения идёт в `extension/module/GT_Data.bsl`, `build/httpservice.json`
и `build/role.json`; готовый `.cfe` пересобирается командой `gfdata.exe -export-extension`
(ей нужна платформа 1С рядом — `.cfe` собирает конфигуратор).

Расширение намеренно **не заимствует язык** расширяемой конфигурации и собрано с низким
режимом совместимости. Это и делает одну сборку пригодной для любой базы: расширение с
собственным языком привязывается к UUID языка конкретной конфигурации и в другую не встаёт,
а режим совместимости выше базы платформа отвергает. Проверено на УТ 11.5 и БП 3.0.

Исходник расширения — описание (`build/httpservice.json`, `build/role.json`,
`extension/module/GT_Data.bsl`), а не готовая выгрузка.

## Установка в базу

```powershell
# файловую базу веб-сервер держит занятой — на время установки его гасят
Stop-Process -Name httpd -Force
gfdata.exe -install "C:\путь\к\базе" -db-user <пользователь> -db-password <пароль>
Start-Process <путь к Apache>\bin\httpd.exe

# серверная база
gfdata.exe -install "сервер\база" -server -db-user <пользователь> -db-password <пароль>
```

Установщик несёт расширение внутри бинаря, сам находит конфигуратор (старшую версию
платформы; иное — флагом `-platform`) и проверяет результат **по журналу конфигуратора**,
а не по коду возврата: `1cv8.exe` — оконное приложение и умеет отрапортовать успехом,
застряв на диалоге.

### Расширение отдельным файлом

Там, где расширение подключает администратор базы, а каналом пользуется обычный
пользователь, установка через `-install` не годится: она идёт режимом конфигуратора и
требует права «Администрирование». Файл выкладывается отдельно:

```
gfdata.exe -export-extension GTData.cfe
```

Дальше — Конфигуратор → Конфигурация → Расширения конфигурации → Добавить из файла.
Платформа рядом нужна: `.cfe` собирается конфигуратором. Если её нет, выгружаются
XML-исходники, и об этом говорится прямо, а не подсовывается молча не тот формат.

### Право на сервис

Доступ к сервису даёт роль `GT_ОсновнаяРоль` — она перечисляет право `Use` по каждому методу
поимённо (13 штук). Без этого права платформа отвечает 401: публичных HTTP-сервисов в
расширении не бывает, проверка встроена в вызов.

**Роль видимая, и выдаётся она в пользовательском режиме через профиль группы доступа:**

1. `Администрирование → Настройки пользователей и прав → Профили групп доступа` — создать
   дополнительный профиль, например «Доступ к данным (gf-data-1c)», и включить в него
   роль `GT_ОсновнаяРоль`;
2. `Группы доступа` — создать группу по этому профилю и добавить в неё пользователя,
   под которым ходит сервер.

Так право видно в интерфейсе, проверяемо и переживает пересчёт ролей.

**Почему не «основная роль».** Она объявлялась основной до 03.09.2026, и доступ получали все
без настройки — удобно ровно до первой беды. Основную роль платформа выдаёт неявно: в списке
ролей пользователя её нет ни когда она работает, ни когда пропала. А в базах на БСП её стирает
пересчёт ролей в подсистеме «Управление доступом» — канал умирает молча, отказом прав, который
неотличим от неверного пароля. Прежний флаг `-StripDefaultRole`, существовавший ровно для
такого случая, при этом **не работал**: каркас `cfe-init` прописывал `DefaultRoles` сам, а флаг
лишь пропускал шаг добавления.

Старое поведение осталось флагом `-DefaultRole` — для базы без БСП, разового стенда или
демонстрации, где профиль заводить негде.

Права на **данные** расширение не выдаёт и не подменяет: их даёт роль пользователя в самой
конфигурации.

## Регистрация базы у сервера

```
bases action=add name=<ключ> url=http://<хост>/<база>/hs/gt-data user=… password=…
```

Реестр лежит в профиле пользователя (`%AppData%/gt-data-1c/bases.json`, права 0600).
Каталог данных называется по-старому намеренно: продукт переименован из `gt-data-1c`,
а данные уже работающих установок переезд не двигает.
Регистрация самого сервера у агента сводится к пути бинарника.

**Пароли в реестре защищены**, а не лежат текстом: на Windows — средствами DPAPI, с меткой
`dpapi:` перед значением. Смысл не в стойкости шифра, а в области действия ключа: DPAPI
привязывает данные к учётной записи, поэтому украденный файл реестра ничего не даёт на другой
машине и под другим пользователем. Вписанный руками открытый пароль тоже принимается — и
защищается при первом же чтении реестра, а не при ближайшей его правке: иначе он лежал бы
открытым месяцами. Если защитить не удалось, канал всё равно работает, а пароль остаётся
открытым — отказывать в работе из-за этого сервер не станет.

**Доменная аутентификация (NTLM) поддержана и включается сама**, если логин выглядит как
`ДОМЕН\пользователь`. Явно способ задаётся полем `auth` (`ntlm` или `basic`) — на случай,
когда догадка по логину неверна. Обычный Basic доменной учётке отвечает отказом прав, который
легко принять за неверный пароль, поэтому догадка тут лучше молчания.

## Запуск в контейнере

Нужен там, где клиент не может запустить бинарь сам: живёт в контейнере, в вебе или на
другой машине. На своей машине проще stdio — клиент поднимает процесс сам.

```bash
docker compose up -d --build     # поднять MCP по HTTP на 127.0.0.1:9077/mcp
docker compose logs -f
```

Настройки — переменными окружения или файлом `.env` рядом: `BIND_HOST` (по умолчанию
петля хоста), `PORT`, `TOKEN` (Bearer-авторизация; пусто — проверки нет), `DATA_DIR`
(реестр баз и журнал), `KB_DB` (база справки платформы).

Три вещи, которые стоит знать заранее:

- **Расширения в образе нет.** Собрать его в Linux нечем, да и незачем: установка в базу —
  разовое действие на машине с платформой 1С, файл лежит в `dist/GTData.cfe`. Сервер
  в контейнере отвечает на данные полностью, а `-install` в нём честно откажет.
- **Пароли в реестре внутри контейнера не защищены.** На Windows их закрывает DPAPI,
  в Linux такого механизма нет — они лежат открытым текстом в файле с правами 0600.
  Каталог `DATA_DIR` держите соответственно.
- **Токена по умолчанию нет.** Пустой `-token` означает «проверки нет»; сервер сам
  предупреждает в журнал, что слушает нелокальный адрес без токена. Зашивать пароль
  в образ хуже, чем не иметь его вовсе: он выглядит защитой, не будучи ею.

## Диагностика

| Флаг | Что делает |
|---|---|
| `-log auto` | вести журнал обращений к базам (`%LocalAppData%/gt-data-1c/server.log`) |
| `-timeout` | сколько ждать базу; по умолчанию 300 с — выгрузка метаданных крупной конфигурации идёт минутами |
| `-registry` | другой файл реестра баз |
| `-version` | версия, путь реестра и путь журнала |

Инструмент `probe` сверяет версию расширения с версией сервера и предупреждает при
расхождении. Это не формальность: старое расширение отвечает на новые методы **пустотой,
а не ошибкой**, и рассинхрон читается как «в базе нет данных».

Ответ базы крупнее 128 МиБ отклоняется с внятным отказом — такой размер почти всегда
означает ошибку запроса, а не большие данные.

## Проверки

```
cargo test --workspace                      # всё: каркас, живые прогоны, приёмка
GT_SKIP_LIVE=1 cargo test --workspace       # без обращения к стендам
cargo run --example cmp_probe               # проба канала к зарегистрированным базам
```

Живые тесты сами пропускаются, если стенд не отвечает: на машине без базы прогон обязан
молчать, а на машине с базой — падать, если база ответила не то. Приёмка сверяет числа
с эталоном, снятым прежним каналом, и проверяет, что все типы объектов, которые он понимал,
понимает и этот.
