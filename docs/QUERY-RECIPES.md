# Рабочие запросы: то, чего нет в справке платформы

Справка вендора учит **конструкции** языка запросов, и с 26.08.2026 инструмент `syntax`
доводит до нужной страницы в 88% случаев. Но запрос за вас она не пишет, и вот почему:

| | |
|---|---|
| страниц `shquery` в справке | 129 |
| **из них с примером запроса** | **35 (27%)** |
| примеров по `ДвиженияССубконто`, `ОборотыДтКт`, `ПЕРИОДАМИ`, вложенным запросам | **0** |
| объекты в примерах | `Документ.РасходнаяНакладная`, `Справочник.Номенклатура` — демо-конфигурация, которой нет ни в УТ, ни в БП |

Пример со страницы «Предложение СГРУППИРОВАТЬ ПО», поданный дословно в `query_check` по УТ 11:

```
ОТКАЗ: Таблица не найдена "Документ.РасходнаяНакладная.Состав"
```

Ниже — запросы, **проверенные исполнением** в живых базах (УТ 11.5 и БП 3.0, платформа
8.3.27.2130), с фактическими числами. Числа приведены не для красоты: по ним видно, что
запрос вернул данные, а не пустоту, которую легко принять за ответ.

---

## Прежде чем писать запрос

Готовые инструменты считают то же самое без языка запросов, и ошибиться синтаксисом в них
нельзя: `register` (итоги регистра накопления), `accounts` (бухгалтерские итоги по счёту),
`slice` (регистр сведений на дату), `count`. Запрос нужен, когда готового не хватает:
соединения, нетиповые разрезы, расчёт внутри запроса.

## 1. Остатки товаров на складах на дату

```sql
ВЫБРАТЬ
	Остатки.Номенклатура КАК Номенклатура,
	Остатки.Склад КАК Склад,
	Остатки.ВНаличииОстаток КАК Количество
ИЗ
	РегистрНакопления.ТоварыНаСкладах.Остатки(&НаДату, ) КАК Остатки
ГДЕ
	Остатки.ВНаличииОстаток > 0
УПОРЯДОЧИТЬ ПО
	Количество УБЫВ
```

**Ресурс переименован:** в регистре он `ВНаличии`, в виртуальной таблице — `ВНаличииОстаток`.
Это общее правило: к остаткам добавляется «Остаток», к оборотам — «Оборот». Точные имена
отдаёт инструмент `object`.

## 2. Продажи с себестоимостью и остатком (временная таблица + ключи аналитики)

Главная ловушка УТ: **в регистре продаж нет измерения «Номенклатура»**. Есть
`АналитикаУчетаНоменклатуры` — ссылка на справочник ключей, откуда номенклатура и достаётся.
Справка платформы про это не скажет никогда: это устройство конфигурации, а не языка.

```sql
ВЫБРАТЬ
	Ключ.Номенклатура КАК Номенклатура,
	СУММА(Об.СуммаВыручкиОборот) КАК Выручка,
	СУММА(Об.СтоимостьОборот) КАК Себестоимость,
	СУММА(Об.КоличествоОборот) КАК Количество
ПОМЕСТИТЬ ВрПродажи
ИЗ
	РегистрНакопления.ВыручкаИСебестоимостьПродаж.Обороты(&Начало, &Конец, , ) КАК Об
	ЛЕВОЕ СОЕДИНЕНИЕ Справочник.КлючиАналитикиУчетаНоменклатуры КАК Ключ
	ПО Об.АналитикаУчетаНоменклатуры = Ключ.Ссылка
СГРУППИРОВАТЬ ПО
	Ключ.Номенклатура
;
ВЫБРАТЬ
	П.Номенклатура КАК Номенклатура,
	П.Количество КАК Продано,
	П.Выручка КАК Выручка,
	П.Себестоимость КАК Себестоимость,
	П.Выручка - П.Себестоимость КАК ВаловаяПрибыль,
	ЕСТЬNULL(Ост.ВНаличииОстаток, 0) КАК ОстатокНаКонец
ИЗ
	ВрПродажи КАК П
	ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.ТоварыНаСкладах.Остатки(&Конец, ) КАК Ост
	ПО П.Номенклатура = Ост.Номенклатура
УПОРЯДОЧИТЬ ПО
	ВаловаяПрибыль УБЫВ
```

Ресурсы регистра называются `СуммаВыручки` и `Стоимость` — не «Выручка» и не «Себестоимость».
`ЕСТЬNULL` обязателен: левое соединение с остатками даёт `NULL` там, где товар распродан,
а арифметика с `NULL` даёт `NULL`, а не ноль.

## 3. Дебиторка по интервалам просрочки (ВЫБОР + РАЗНОСТЬДАТ + ИТОГИ)

```sql
ВЫБРАТЬ
	Ключ.Партнер КАК Партнер,
	Ост.ДатаПлановогоПогашения КАК СрокОплаты,
	ВЫБОР
		КОГДА Ост.ДатаПлановогоПогашения = ДАТАВРЕМЯ(1, 1, 1) ТОГДА "без срока"
		КОГДА Ост.ДатаПлановогоПогашения >= &НаДату ТОГДА "не просрочено"
		КОГДА РАЗНОСТЬДАТ(Ост.ДатаПлановогоПогашения, &НаДату, ДЕНЬ) <= 30 ТОГДА "до 30 дней"
		КОГДА РАЗНОСТЬДАТ(Ост.ДатаПлановогоПогашения, &НаДату, ДЕНЬ) <= 90 ТОГДА "31-90 дней"
		ИНАЧЕ "свыше 90 дней"
	КОНЕЦ КАК Интервал,
	СУММА(Ост.ДолгОстаток) КАК Долг
ИЗ
	РегистрНакопления.РасчетыСКлиентамиПоСрокам.Остатки(&НаДату, ) КАК Ост
	ЛЕВОЕ СОЕДИНЕНИЕ Справочник.КлючиАналитикиУчетаПоПартнерам КАК Ключ
	ПО Ост.АналитикаУчетаПоПартнерам = Ключ.Ссылка
ГДЕ
	Ост.ДолгОстаток <> 0
СГРУППИРОВАТЬ ПО
	Ключ.Партнер, Ост.ДатаПлановогоПогашения
ИТОГИ
	СУММА(Долг)
ПО
	ОБЩИЕ, Партнер
```

Пустая дата — это `ДАТАВРЕМЯ(1, 1, 1)`, а не `NULL` и не пустая строка. Порядок ветвей `ВЫБОР`
важен: выигрывает первое сработавшее условие.

## 4. Задолженность покупателей по счёту с субконто (регистр бухгалтерии)

```sql
ВЫБРАТЬ
	Дв.Субконто1 КАК Контрагент,
	Дв.Субконто2 КАК Договор,
	СУММА(Дв.СуммаОборотДт) КАК Отгружено,
	СУММА(Дв.СуммаОборотКт) КАК Оплачено,
	СУММА(Дв.СуммаКонечныйОстатокДт) КАК ДолгНаКонец
ИЗ
	РегистрБухгалтерии.Хозрасчетный.ОстаткиИОбороты(
		&Начало, &Конец, , ,
		Счет = ЗНАЧЕНИЕ(ПланСчетов.Хозрасчетный.РасчетыСПокупателями),
		, ) КАК Дв
СГРУППИРОВАТЬ ПО
	Дв.Субконто1, Дв.Субконто2
ИМЕЮЩИЕ
	СУММА(Дв.СуммаКонечныйОстатокДт) <> 0
УПОРЯДОЧИТЬ ПО
	ДолгНаКонец УБЫВ
```

План счетов адресуется как `ПланСчетов.Хозрасчетный`, **без** префикса `Справочник`.
Счёт задаётся предопределённым значением, а не кодом-строкой.

**Сверка:** сумма по контрагентам совпала с конечным остатком, который отдаёт инструмент
`accounts` по счёту 62.01 за тот же период. Такую сверку стоит делать всегда — она ловит
и потерянный отбор, и задвоение при соединении.

## 5. Корреспонденции счетов за период (ОборотыДтКт)

Примеров этой таблицы в справке нет ни одного.

```sql
ВЫБРАТЬ
	Кор.СчетДт КАК СчетДебета,
	Кор.СчетКт КАК СчетКредита,
	СУММА(Кор.СуммаОборот) КАК Сумма
ИЗ
	РегистрБухгалтерии.Хозрасчетный.ОборотыДтКт(&Начало, &Конец, , , , , , ) КАК Кор
СГРУППИРОВАТЬ ПО
	Кор.СчетДт, Кор.СчетКт
УПОРЯДОЧИТЬ ПО
	Сумма УБЫВ
```

Сигнатура: `ОборотыДтКт(Начало, Конец, Периодичность, УсловиеДт, СубконтоДт, УсловиеКт,
СубконтоКт)` — условия по дебету и кредиту **раздельные**, в отличие от `ДвиженияССубконто`,
где условие одно и общее.

## 6. Движения регистра с документом-регистратором

Регистратора нет ни в одной виртуальной таблице — он есть только у самих движений.

```sql
ВЫБРАТЬ
	Дв.Период КАК Период,
	Дв.Регистратор КАК Документ,
	Дв.Номенклатура КАК Номенклатура,
	ВЫБОР КОГДА Дв.ВидДвижения = ЗНАЧЕНИЕ(ВидДвиженияНакопления.Приход)
		ТОГДА "приход" ИНАЧЕ "расход" КОНЕЦ КАК Вид,
	Дв.ВНаличии КАК Количество
ИЗ
	РегистрНакопления.ТоварыНаСкладах КАК Дв
ГДЕ
	Дв.Период МЕЖДУ &Начало И &Конец
	И Дв.Активность
УПОРЯДОЧИТЬ ПО
	Период УБЫВ
```

`Активность` проверять обязательно: неактивные движения в таблице остаются, но в итоги
не входят — выборка без этого условия разойдётся с любой виртуальной таблицей.

# Отрицательные примеры: запросы, которые выполняются и врут

Синтаксическую ошибку платформа назовёт. Эти случаи она **не заметит**, и результат будет
выглядеть как честный ответ базы.

## О-1. Ссылка, сравненная со строкой, — ноль строк без ошибки

```sql
ВЫБРАТЬ КОЛИЧЕСТВО(*) ИЗ Справочник.Номенклатура КАК Н
ГДЕ Н.Ссылка = "Кабель ВВГнг 3х1.5"        -- 0 строк, ошибки нет
```

Проверено на живой базе рядом с верным вариантом:

| условие | найдено строк |
|---|---|
| `Н.Ссылка = "…"` (строка) | **0** |
| `Н.Наименование = "…"` | **1** |

Ссылка сравнивается со ссылкой: параметром-объектом или
`ЗНАЧЕНИЕ(Справочник.X.ИмяПредопределённого)`. Пустой ответ здесь неотличим от «в базе такого
нет» — и именно поэтому опасен.

## О-2. Граница периода: остаток «на дату» не включает движения этой даты

Самая тихая из ошибок: отчёт сходится сам с собой и расходится с оборотами ровно на движения
последнего дня.

```sql
Остатки(ДАТАВРЕМЯ(2026,6,23))            -- остаток на НАЧАЛО дня 23.06
Остатки(ДАТАВРЕМЯ(2026,6,23,23,59,59))   -- остаток на конец дня
```

Проверено числами на одной номенклатуре:

| момент | остаток |
|---|---|
| на 23.06 (дата без времени) | **141** |
| на 23.06 23:59:59 | **140** |
| движение за 23.06 | **−1** |

Разница ровно в движении этого дня. Для остатков «на конец периода» берите
`КОНЕЦПЕРИОДА(&Дата, ДЕНЬ)` либо границу следующего дня.

## О-3. Поле основной таблицы в виртуальной

```sql
ВЫБРАТЬ Ост.Регистратор ИЗ РегистрНакопления.ТоварыНаСкладах.Остатки(&Д, ) КАК Ост
```

Здесь платформа отказывает — случай честный. Важно другое: **виртуальных таблиц с именем
«Остатки» две разных**, у регистра накопления и у регистра бухгалтерии, и состав полей
у них не совпадает. Подсказка сервера различает их с 26.08.2026; до этого она отвечала
бухгалтерскими `Счет` и `Субконто` на вопрос о товарном регистре — то есть уверенно называла
поля, которых там нет.

---

## Как проверять свой запрос

1. `query_check` — разбирает синтаксис и показывает колонки, **не обращаясь к данным**;
2. `query` с малым `limit` — убедиться, что строки вообще есть;
3. сверка с готовым инструментом (`register`, `accounts`) — итог обязан совпасть.

Пустой результат — это не ответ. Пока не отличили «данных нет» от «запрос не тот», числа
из него брать нельзя.
